## 1. О проекте

### 1.1. Что это
**AquaMind** — открытый аппаратно-программный комплекс для автоматизации аквакультуры: установок замкнутого водоснабжения (УЗВ) и аквариумов. Написан на Go.

- **Формат:** дипломный проект буткемпа VK Education, трек «Микросервисы на Go».
- **Команда:** Антон Бабаев, Роман Забелин.
- **Статус:** этап проектирования. Зоны ответственности распределяются, финальное распределение фиксируется на текущей неделе.

### 1.2. Проблема
- Рынок УЗВ растёт, а автоматизация остаётся «узким горлышком».
- Коммерческие решения закрыты и привязывают к поставщику (vendor lock-in).
- Существующие open-source проекты «игрушечные» и монолитные, к реальной нагрузке не готовы.

### 1.3. Цель
Создать профессиональный open-source комплекс на Go для автоматизации фермерских УЗВ: надёжность промышленного уровня при доступности свободного ПО.

### 1.4. Задачи
1. Спроектировать и реализовать автономный Edge-контроллер на Raspberry Pi, который работает без связи с сервером.
2. Отделить бизнес-логику от оборудования через HAL, чтобы замена симулятора на реальные датчики не требовала правки правил.
3. Обеспечить воспроизводимое демо через сценарную симуляцию на CSV.
4. Реализовать надёжную доставку данных на сервер: локальное хранение, досылка, защита от дублей.
5. Защитить управление (control plane) от удалённого доступа.
6. Показать навыки трека: слоистая архитектура, DI через интерфейсы, конкурентность, graceful shutdown, работа с железом.

### 1.5. Учебная цель
Применить знания микросервисной архитектуры и Go на прикладной задаче. Проект демонстрирует слоистую архитектуру, конкурентность (горутины, каналы, `sync.RWMutex`) и работу с оборудованием.

## 2. Объём MVP и приоритеты

По рекомендации куратора **фокус MVP — Edge**: там основная инженерная сложность. Backend стандартный, поэтому делается минимальным. Полная система из трёх сервисов описывается как план развития.

| Приоритет | Что входит |
|---|---|
| **Обязательно (Edge)** | Сценарии Control, Safety, Alert, Settings, Sync. Политики подогрева и тревог с гистерезисом. Сценарная симуляция CSV. Светодиоды на GPIO. SQLite + outbox. Настройки через middleware «только LAN». Graceful shutdown с переводом железа в безопасное состояние |
| **Желательно (минимальный Backend)** | Один эндпоинт приёма пакета с дедупликацией и запись в PostgreSQL. Отправка алертов в Telegram |
| **Если останется время** | Frontend: одна HTMX-страница с последними показаниями и алертами. Графики — по остатку времени |
| **После защиты (рассказать, не делать)** | Modbus RTU/TCP, адаптивная калибровка pH/DO, аппаратный watchdog, Docker, CI/CD, документация для контрибьюторов |

### 2.1. Демо-железо
- Только светодиоды на GPIO: **жёлтый** — подогрев, **красный** — тревога, **зелёный** — норма.
- Насос и УФ-лампа считаются **постоянно включёнными** (флаг в конфигурации). Rule Engine управляет только подогревом и тревогами.

### 2.2. Предварительное разделение работы
| Участник | Зона |
|---|---|
| Антон Бабаев | Ядро Edge: доменные политики, Control, Safety, Alert, HAL, SimulationProvider |
| Роман Забелин | Инфраструктура Edge: SQLite, outbox, Sync, Settings + middleware. Минимальный Backend |
| Frontend | В последнюю очередь, кто освободится |

Единственная точка договорённости на старте — сущности Edge (`SensorReading` и др.), интерфейс `SensorSource` и формат CSV.

## 3. Правила работы над кодом

### 3.1. Базовые правила (зафиксированы командой)
1. Работаем в рамках **трёх сервисов**: Edge, Backend, Frontend. Новые сервисы не добавляем.
2. Связь Edge → Backend — **HTTP/REST + JSON**, Edge сам отправляет данные (push). **Не MQTT.**
3. Симуляция — **сценарная, по CSV**. Случайные генераторы не используются.
4. Внутри каждого сервиса — слои **delivery → usecase → repository/adapter**, DI через интерфейсы.
5. Бизнес-логика **не знает, откуда данные**: работает только с интерфейсами HAL.
6. Технические названия таблиц и функций — в коде. В объяснениях — принципы.
7. Архитектуру не меняем без явного решения команды.

### 3.2. Технические соглашения
8. **Интерфейсы объявляет потребитель** — пакет usecase (файл `ports.go`). Реализации лежат в `adapter/`.
9. **Entity не импортирует ничего**, кроме стандартной библиотеки. **Перевод Entity ↔ DTO** — только на границах: HTTP-обработчики и HTTP-клиенты. Use case о DTO не знает.
10. **Сущности у каждого сервиса свои.** Общий между сервисами только JSON-контракт синхронизации (`internal/contract/syncv1`).
11. **Время** — UTC, точность до миллисекунд. Время показания ставится **в момент чтения**, а не берётся из CSV.
12. Показание, состояние выходов, алерты и запись в outbox сохраняются **одной транзакцией**. Отметка «отправлено» ставится только после ответа **2xx**.
13. **Правила безопасности главнее правил комфорта.** Пороги работают с гистерезисом, повторно алерты не создаются.
14. `context.Context` передаётся во все долгие операции. При остановке железо переводится в безопасное состояние.
15. Названия пакетов не совпадают со стандартной библиотекой: `uplink` / `ingest` / `syncv1` вместо `sync`.
16. Доменные политики — чистые функции, покрываются табличными тестами.

## 4. Архитектура системы

### 4.1. Состав
```
                       ┌────────────── Raspberry Pi 3 B+ ──────────────┐
 Ноутбук в LAN ──HTTP──▶│  Edge (Go)  ◀── CSV-сценарий                  │
 (настройка порогов,    │     │  ▲                                      │
  только LAN)           │     ▼  │                                      │
                        │  GPIO-светодиоды      SQLite (WAL)           │
                        └─────┬─────────────────────────────────────────┘
                              │ HTTP POST · JSON (push) · SyncBatch
                              ▼
                        Backend (Go) ──▶ PostgreSQL
                              │
                              ├──▶ Telegram API ──▶ фермер
                              ▲
                              │ HTTP GET (опционально)
                        Frontend (Go + HTMX) ◀── браузер оператора
```

### 4.2. Роли сервисов
| Сервис | Где работает | Роль | Хранит данные |
|---|---|---|---|
| **Edge** | Raspberry Pi 3 B+ | Автономный источник правды: читает датчики, применяет правила, управляет выходами, копит данные и досылает | SQLite |
| **Backend** | Сервер / ноутбук | Принимает пакеты с дедупликацией, хранит историю, шлёт алерты в Telegram, отдаёт API | PostgreSQL |
| **Frontend** | Сервер / ноутбук | Читает API Backend, показывает показания и алерты | Нет |

### 4.3. Ключевые свойства
- **Направление связей:** Edge → Backend ← Frontend. Backend никого не вызывает, циклов нет.
- **Push от Edge:** Edge не открывает порты в интернет, Backend не ходит к Edge.
- **Оффлайн-автономность:** без связи с Backend правила и светодиоды работают локально, данные копятся в outbox и досылаются после восстановления связи.
- **Алерты:** создаются на Edge (красный светодиод загорается сразу), в Telegram отправляются Backend после синхронизации. **Без связи сообщение в Telegram придёт с задержкой** — прямое следствие модели «Edge автономен, в интернет смотрит только Backend».

## 5. Edge — слоистая архитектура

### 5.1. Слои
| Слой | Что содержит | Пакеты |
|---|---|---|
| **Delivery** | Внешние триггеры: таймеры-горутины, HTTP-обработчики | `delivery/` |
| **UseCase** | Сценарии | `usecase/<сценарий>/` |
| **Порты** | Интерфейсы, объявленные в usecase | `usecase/<сценарий>/ports.go` |
| **Adapter** | Реализации портов | `adapter/` |
| **Infrastructure** | Внешние ресурсы: CSV-файл, GPIO-пины, файл SQLite, Backend в сети | вне кода (кроме миграций) |
| **Entity** | Доменные сущности и политики | `domain/`, `domain/policy/` |
| **DTO** | Форматы на сетевых границах | `delivery/http/dto.go`, `contract/syncv1` |

Стрелки вызовов идут сверху вниз. Зависимости в коде между Adapter и портами направлены **вверх**: адаптер реализует интерфейс usecase (DIP).

### 5.2. Сценарии (use case)
Rule Engine разбит на отдельные сценарии по замечанию куратора: один большой use case неудобен в работе и тестировании.

| Сценарий | Триггер (Delivery) | Ответственность |
|---|---|---|
| **ControlUsecase** | `SensorPoller` — тик опроса | Прочитать датчики → применить политики → выставить выходы → сохранить одной транзакцией. **Единственный владелец выходов** |
| **AlertUsecase** (tracker) | Вызывается из Control | Жизненный цикл алерта: поднять один раз, снять при возврате в норму. Ничего не сохраняет сам |
| **SafetyUsecase** | `SafetyWatchdog` — свой тик | Данные устарели или датчик выдаёт ошибку → просит Control перейти в Safe Mode |
| **SettingsUsecase** | `Handler.Settings` — HTTP | Чтение и смена порогов с валидацией |
| **SyncUsecase** (пакет `uplink`) | `SyncWorker` — тик + backoff | Взять пакет из outbox → отправить → пометить после 2xx |

**Почему Safety — отдельный сценарий со своим тиком:** если чтение датчика зависнет, тик Control не наступит, и проверять свежесть данных изнутри Control бессмысленно.

**Почему Safety не управляет выходами напрямую:** если выходами управляют два сценария, они могут одновременно выставить противоположные состояния. Safety вызывает Control через узкий интерфейс `SafeModeController`.

> Условие реализации: Control **не держит блокировку во время чтения датчиков**, иначе Safe Mode не включится при зависшем чтении.

### 5.3. Порты (интерфейсы)
| Порт | Объявлен в | Реализация |
|---|---|---|
| `SensorSource` | control | `SimulationProvider`, в будущем `ModbusScanner` |
| `Actuators` | control | `GPIOLEDProvider`, `console` (заглушка для разработки) |
| `Store` (узкие интерфейсы по сценариям) | control, settings | `SQLiteRepository` |
| `AlertTracker` | control | `alert.Tracker` |
| `SafeModeController` | safety | `ControlUsecase` |
| `Outbox` | uplink | `SQLiteRepository` |
| `Uploader` | uplink | `BackendClient` |

На схеме нарисован один `Store`, но в коде каждый сценарий объявляет только нужные ему методы. Все узкие интерфейсы реализует один `SQLiteRepository`.

```go
// internal/edge/usecase/control/ports.go
type SensorSource interface {
	Read(ctx context.Context) (domain.SensorReading, error)
}

type Actuators interface {
	Apply(ctx context.Context, s domain.ActuatorState) error
}

type Store interface {
	// Показание, состояние, алерты и записи outbox — одной транзакцией.
	SaveTick(ctx context.Context, r domain.SensorReading, s domain.ActuatorState, alerts []domain.Alert) error
	LoadThresholds(ctx context.Context) (domain.Thresholds, error)
}
```

### 5.4. HAL
HAL — **два интерфейса**: `SensorSource` (чтение) и `Actuators` (выходы). Единого «Hardware» нет.

**Почему:** симулятор умеет только читать, GPIO — только управлять. Единый интерфейс не закрывает ни одна реализация. Разделение позволяет заменить источник показаний на Modbus, оставив светодиоды на GPIO, без правки кода правил.

**Раскладка по слоям** (ответ на вопрос куратора):
- `SensorSource`, `Actuators` — интерфейсы (порты), объявлены в usecase.
- `SimulationProvider`, `GPIOLEDProvider`, `ModbusScanner` — реализации, **слой Adapter**.
- CSV-файл, GPIO-пины со светодиодами, шина Modbus — **слой Infrastructure**.

### 5.5. Сущности Edge
| Сущность | Поля (смысл) |
|---|---|
| `SensorReading` | температура, поток, кислород, pH, время чтения (UTC) |
| `ActuatorState` | подогрев, тревога, норма, Safe Mode |
| `Alert` | тип, уровень, сообщение, время, состояние (поднят / снят) |
| `Thresholds` | пороги и гистерезис — настройки правил, метод `Validate()` |

**pH** хранится и показывается, правил для него в MVP нет. Пригодится для калибровки pH/DO из roadmap.

### 5.6. Доменные политики и порядок правил
Политики — чистые функции «показание + текущее состояние + пороги → решение»:
- `HeatingPolicy` — гистерезис, критические температуры, отсутствие потока.
- `AlarmPolicy` — кислород, критические состояния.

**Порядок применения (верхнее главнее):**

| # | Условие | Подогрев | Индикация | Алерт |
|---|---|---|---|---|
| 1 | **Safe Mode**: данные устарели или ошибка датчика | выкл | красный | да |
| 2 | **Нет потока** при включённом насосе | выкл (защита от перегрева без циркуляции) | красный | да |
| 3 | **Критически высокая температура** | выкл | красный | да |
| 4 | **Критически низкая температура** | вкл | красный | да |
| 5 | **Мало кислорода** | не влияет | красный | да |
| 6 | **Низкая температура** | вкл ниже порога, выкл выше «порог + гистерезис» | жёлтый | нет |

**Индикация:**
- жёлтый — подогрев включён;
- красный — есть активный алерт;
- зелёный — активных алертов нет.

Жёлтый и красный могут гореть одновременно (например, холодно и мало кислорода).

**Алерты:** поднимаются один раз при входе в состояние и снимаются при выходе из него. Защита от спама при шумных данных.

**Значения порогов** — `[TBD]`, задаются в `configs/edge.yaml`.

### 5.7. Хранение и синхронизация
- **SQLite в режиме WAL** с `busy_timeout`: `SensorPoller` пишет, `SyncWorker` читает и обновляет параллельно.
- **Драйвер на чистом Go (без CGO)** — упрощает кросс-компиляцию под ARM.
- **Outbox:** запись в очередь отправки в той же транзакции, что и показание. Отметка «отправлено» — только после 2xx. Получаем доставку «хотя бы раз», а дедупликация на Backend делает её фактически однократной.
- **Backoff:** при недоступном Backend `SyncWorker` увеличивает паузу между попытками. Размер пакета ограничен.
- **Очистка:** отправленные записи периодически удаляются — против роста базы и износа SD-карты.
- **Интервал опроса для демо:** 1–5 секунд.

### 5.8. Control plane и безопасность
- `Handler.Settings` (GET/PUT порогов) закрыт middleware, которое пропускает только **localhost и LAN-подсети** из конфигурации.
- Адрес проверяется **по реальному адресу соединения (`RemoteAddr`)**, а не по заголовкам вроде `X-Forwarded-For`, которые можно подделать.
- Формулировка для защиты: **«изоляция control plane на сетевом уровне»**. Формулировка «только при физическом подключении» — преувеличение: middleware пускает всех из локальной сети. Из речи она убрана.

### 5.9. Конкурентность
- Горутины: `SensorPoller`, `SafetyWatchdog`, `SyncWorker`, HTTP-сервер. Общий `context`.
- `sync.RWMutex`: пороги и текущее состояние в Control. Settings пишет, тики читают.
- Каналы — для координации остановки и сигналов между горутинами.

### 5.10. Graceful shutdown (порядок)
1. Отменить контекст, остановить опрос и watchdog.
2. Перевести железо в безопасное состояние: **подогрев выключен**, светодиоды в понятном состоянии.
3. Последняя попытка синхронизации с таймаутом.
4. Остановить HTTP-сервер.
5. Закрыть базу.

## 6. Backend — слоистая архитектура (минимальный)

| Слой | Блоки |
|---|---|
| Delivery | `Handler.PostSync` (SyncBatchDTO → Entity), `Handler.GetReadings` (опционально, для Frontend) |
| UseCase | `ingest` — приём с дедупликацией, `alert` — антиспам и текст уведомления |
| Порты | `Store` (запись с дедупом), `ReadStore` (история за период), `Notifier` |
| Adapter | `PostgresRepository`, `TelegramNotifier` (Entity → текст сообщения) |
| Infrastructure | PostgreSQL, Telegram API |
| Entity | `Reading` (+ client_id), `Alert` (+ статус отправки в Telegram) — **свои, не общие с Edge** |

- **Дедупликация:** уникальность по `(client_id, timestamp)`, вставка `INSERT … ON CONFLICT DO NOTHING`.
- **Поток алертов:** `ingest` принимает пакет → новые алерты передаются в `alert` → `Notifier` → Telegram.
- **Исключение из правила слоёв:** `Handler.GetReadings` читает данные через `ReadStore` **без use case**, так как бизнес-логики в чтении нет. DI через интерфейс сохраняется.

## 7. Frontend

Go + HTML/HTMX + Tailwind. Данные не хранит, бизнес-логики нет. Внутри — шаблоны и клиент к API Backend. Отдельной слоистой схемы не получает: слоистая архитектура здесь избыточна. **В MVP опционален.**

## 8. Контракт синхронизации Edge → Backend (черновик)

Пакет `internal/contract/syncv1` — **единственный общий код** между сервисами.

```json
{
  "client_id": "edge-01",
  "sent_at": "2026-11-21T10:00:05.123Z",
  "readings": [
    { "ts": "2026-11-21T10:00:00.000Z", "temp_c": 23.4, "flow_lpm": 12.0, "o2_mgl": 6.8, "ph": 7.1 }
  ],
  "alerts": [
    { "ts": "2026-11-21T10:00:00.000Z", "type": "o2_low", "severity": "critical",
      "message": "Кислород ниже порога", "state": "raised" }
  ]
}
```

- Ключ дедупликации — `client_id` + `ts`.
- `AlertDTO` — часть пакета синхронизации и ответа API. Текст для Telegram формирует `TelegramNotifier`, а не DTO.
- Поля — черновик, фиксируются при реализации `syncv1`.

## 9. Сценарная симуляция (CSV)

**Формат:**
```csv
offset_sec,temp_c,flow_lpm,o2_mgl,ph
0,24.1,12.0,7.2,7.2
60,23.9,12.1,7.1,7.2
```

- Сценарии: `day_cycle.csv` (сутки: ночной спад температуры с шумом, колебания pH, просадки кислорода), `no_flow.csv` (короткий аварийный сценарий).
- `SimulationProvider` читает сценарий **с заданной скоростью** (ускорение времени) и умеет **повторять** его.
- Из CSV берутся **только значения и ритм**. Время ставится в момент чтения (`now()`), поэтому при повторном прогоне Backend не отбросит данные как дубли.
- Гарантирует срабатывание всех правил на демо и даёт 100% воспроизводимость.

## 11. Журнал решений

| # | Решение | Обоснование | Источник |
|---|---|---|---|
| D1 | Три сервиса: Edge, Backend, Frontend | Edge автономен, Backend агрегирует, Frontend развивается независимо | Команда |
| D2 | Edge → Backend по HTTP/JSON, push | Простота, Edge не открывает порты наружу | Команда |
| D3 | Сценарная симуляция на CSV, не рандом | Воспроизводимость демо, гарантированное срабатывание правил | Команда |
| D4 | HAL из двух интерфейсов: SensorSource и Actuators | Ни одна реализация не закрывает единый интерфейс. Замена датчиков не трогает выходы | Разбор схемы, подтверждено куратором |
| D5 | Rule Engine разбит на сценарии Control / Alert / Safety / Settings / Sync | Перегруженный use case неудобен в работе и тестах | Куратор |
| D6 | Правила — доменные политики (чистые функции) | Тестируемость, отделение решений от сценариев | Куратор + разбор |
| D7 | Только Control управляет выходами. Safety — через узкий интерфейс | Исключает конфликт двух владельцев выходов | Разбор схемы v3 |
| D8 | Алерты создаются на Edge, в Telegram — через Backend после синхронизации | AlertUsecase и Notifier на Backend, между ними сеть | Разбор схемы |
| D9 | Сущности у каждого сервиса свои. Общий только `syncv1` | Иначе получается распределённый монолит | Куратор |
| D10 | Маппинг DTO ↔ Entity на границах, use case о DTO не знает | Изменение JSON не трогает бизнес-логику | Разбор схемы |
| D11 | Реализации портов в Adapter, внешние ресурсы в Infrastructure | Совпадает с референсом Clinic, снимает вопрос о месте GPIOLEDProvider | Куратор |
| D12 | Три схемы: система, Edge, Backend. Frontend — блок на схеме системы | Слоистая схема описывает один процесс | Куратор |
| D13 | Фокус MVP на Edge, Backend минимальный, Frontend опционален | Не распыляться, сложность в Edge | Куратор |
| D14 | GetReadings без use case — явное исключение | Чтение без бизнес-логики, DI сохраняется | Команда |
| D15 | Критическая температура — две границы (низкая и высокая) | Для холода и перегрева нужны противоположные действия | Разбор |
| D16 | pH хранится и показывается, правил нет | Уже есть в CSV, нужен для будущей калибровки | Разбор |
| D17 | HealthMonitor / Safe Mode реализуются как SafetyUsecase | Тезис уже есть на слайде, отдельный сервис не нужен | Разбор |
| D18 | Один репозиторий, один Go-модуль, три программы в `cmd/` | Один CI, контракт в одном месте, проще работать вдвоём | Разбор |
| D19 | Время чтения ставится в `now()`, не из CSV | Иначе повтор сценария ломает дедупликацию | Разбор |
| D20 | Формулировка «изоляция control plane на сетевом уровне» | «Физическое подключение» — преувеличение | Разбор |

## 12. Известные риски и ограничения

| Риск | Последствие | Меры |
|---|---|---|
| У Raspberry Pi 3 B+ нет аппаратных часов | После перезагрузки без сети время может быть неверным, а оно часть ключа дедупа | Для демо — знать и проговорить. После защиты — RTC-модуль или NTP-проверка (roadmap) |
| Алерты в Telegram без связи | Задерживаются до восстановления связи | Светодиод загорается сразу. Проговорить на защите как осознанный компромисс |
| Конкурентная запись в SQLite | Ошибки `database is locked` | WAL + busy_timeout |
| Износ SD-карты, рост БД | Отказ носителя, переполнение | Интервал опроса 1–5 с, очистка отправленного |
| CGO-драйвер SQLite | Сложная кросс-компиляция под ARM | Драйвер на чистом Go |
| Шум данных у порога | Дребезг подогрева, спам алертами | Гистерезис, однократные алерты |
| Middleware «только LAN» | Пускает всех из локальной сети, включая Wi-Fi | Корректная формулировка, проверка по `RemoteAddr` |
| Аварийная остановка | Подогрев остаётся включённым | Graceful shutdown переводит железо в безопасное состояние |

## 13. План реализации

1. **Каркас и контракты:** структура репозитория, сущности Edge, порты `SensorSource` / `Actuators`, пороги в конфигурации.
2. **Доменные политики** `HeatingPolicy` и `AlarmPolicy` + табличные тесты на каждое правило и каждый конфликт.
3. **SimulationProvider** и формат CSV — параллельно с п. 2.
4. **ControlUsecase + AlertTracker + SensorPoller + console-заглушка** — полный цикл виден в терминале без железа.
5. **SafetyUsecase + SafetyWatchdog.**
6. **SQLite + outbox** (транзакция тика).
7. **SettingsUsecase + Handler.Settings + middleware LAN.**
8. **GPIOLEDProvider** на Pi.
9. **Uplink (SyncUsecase) + BackendClient**, на Backend — `ingest` с дедупом.
10. **Алерты в Telegram.**
11. **Graceful shutdown** и сборка под Pi (systemd).
12. **Frontend** — если останется время.

## 17. Глоссарий

| Термин | Значение |
|---|---|
| УЗВ | Установка замкнутого водоснабжения |
| Edge | Контроллер на Raspberry Pi, работает автономно |
| HAL | Hardware Abstraction Layer — интерфейсы между логикой и железом |
| Порт | Интерфейс, объявленный в use case |
| Адаптер | Реализация порта для конкретной технологии |
| Outbox | Локальная очередь записей на отправку в Backend |
| Control plane | Управляющий интерфейс: изменение порогов правил |
| Safe Mode | Безопасное состояние: подогрев выключен, тревога, алерт |
| Гистерезис | Разница между порогами включения и выключения против дребезга |
| Дедупликация | Отбрасывание повторно присланных данных по `client_id + timestamp` |
| DIP | Принцип инверсии зависимостей |
